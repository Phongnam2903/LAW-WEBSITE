**Important — Next.js 16 breaking changes vs. common prior knowledge:** the framework ships an `AGENTS.md`/`CLAUDE.md` pointer (auto-regenerated by `next dev`, intentionally committed) instructing any AI agent to read `frontend/node_modules/next/dist/docs/` before writing routing code, because file conventions changed from Next.js 14/15. ## Rendering Strategy

- **Public marketing routes** (home, lawyers, services, insights, case studies, contact — per `docs/ui/01-information-architecture.md`): Server Components by default, SSR/SSG-eligible, matching the SEO requirement in `docs/11-system-design-document.md`.
- **Internal workspace routes** (`/app/*` — dashboard, leads, cases, appointments, etc.): Client Components behind auth, CSR-heavy. Not built in Phase 3.
- No rendering strategy decision beyond "Server Components by default, Client Components where interactivity/auth requires it" is imposed at this stage — App Router's per-component boundary makes this a per-feature decision in later phases, not a global config.

## Route Organization Strategy

Two route groups are recommended for when business screens are built (not created yet, since no real screens exist to organize):

```text
app/
├── (public)/      # marketing site — SSR/SSG, no auth
├── (auth)/        # /login, /forgot-password, /403
└── (app)/         # authenticated internal workspace, CSR + route guards
```

This maps directly to the three route groups identified in the Phase 2 IA (Public site, Auth, Internal workspace under `/app/*`). Route groups (`(name)`) are used so the group name is omitted from the URL, matching the flat public URLs (`/lawyers`, `/services/...`) specified in `docs/ui/01-information-architecture.md`. This structure is documented here as the plan; the actual `(public)`/`(auth)`/`(app)` folders are **not created yet** since an empty route group with no page is not meaningful scaffolding — they will be added when the first real route in each group is built.

## API Client Strategy

- `src/services/api-client.ts` exposes a single `apiRequest<T>(path, options)` helper wrapping `fetch`, prefixing every call with `/api/v1` (matching `docs/10-openapi.yaml` `servers[0].url`) and the configured `NEXT_PUBLIC_API_BASE_URL`.
- Errors are normalized into an `ApiError` class carrying `status`/`code`/`message`, parsed from the backend's `ErrorResponse` schema (`error`, `message`, `status`).
- Auth is handled by an optional `accessToken` parameter (bearer header) — no token storage, refresh logic, or login flow is implemented (that is a business feature, out of Phase 3 scope per the Strict Scope Boundary).
- No data-fetching library (React Query/SWR) is included — see `TF-OQ-006`. Native `fetch` plus Server Components covers the read-only foundation validation; adding a client-side cache library is deferred until the internal workspace's interaction patterns are known.

## Environment Strategy

- `src/config/env.ts` reads and validates `NEXT_PUBLIC_API_BASE_URL` at import time (throws if missing), so a misconfigured environment fails fast rather than silently calling a wrong/undefined URL.
- `.env.example` documents the one required variable; `.env.local` (gitignored) holds the real local value. Full cross-app environment convention is defined in `09-environment-configuration.md`.

## Styling Strategy

- Tailwind CSS v4, CSS-first configuration via `@theme` in `src/styles/globals.css` — no `tailwind.config.js`.
- Design tokens transcribed from `docs/ui/06-design-system.md`: color palette (`navy`, `charcoal`, `neutral`, `gold`/`bordeaux` accent candidates, semantic `success`/`warning`/`danger`/`info`), and border-radius scale (`sm`/`md`/`lg`/`pill`). **All values are PROPOSED** per the source doc (pending `UI-OQ-001`/`UI-OQ-012`) — safe for scaffolding, not final brand values.
- Accent color: `gold-600` is wired as the active token (matches "candidate A" in the design system doc); `bordeaux-700` is defined alongside it so switching the accent later is a one-line change in `globals.css`, not a rework.
- Typography: `Inter` (sans, body/UI) and `Playfair Display` (serif, headings) loaded via `next/font/google`, replacing the `create-next-app` default Geist fonts, matching the two-typeface direction in the design system doc.
- Spacing scale: Tailwind v4's default spacing (4px/0.25rem increments) is used as-is — it already matches the design system's 8px-based scale (all documented `space.*` values are multiples of 4px), so no override was needed.
- Breakpoints: Tailwind v4 defaults (`sm` 640 / `md` 768 / `lg` 1024 / `xl` 1280 / `2xl` 1536) are used as-is. `md` (768px) aligns with the documented tablet reference point; exact final breakpoints are pending `OQ-28` per `docs/03-nfr.md`, so no custom breakpoint scale was hard-coded.

## Component Boundaries

- `components/ui/` — presentation-only, no business/domain knowledge, no data fetching (Button, Input, Badge, Card primitives — per `docs/ui/07-component-inventory.md` "Foundation"/"Form"/"Feedback" categories).
- `components/shared/` — composed from `ui/`, still domain-agnostic (Header, Footer, Sidebar, Pagination — "Navigation" category).
- `features/<feature>/` — domain-specific components, hooks, and services for one business feature (e.g. `features/leads/`), composed from `components/ui` and `components/shared`. Not created yet — first entry lands with the first real feature in a later phase.
